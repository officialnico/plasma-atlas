§ 01

Kokkos: write the loop once.

Performance portability

Before any physics, a piece of pure software engineering. Kokkos is a C++ library from Sandia National Labs. Its job is letting you write one version of a numerical loop and have it run efficiently on a laptop CPU, a Frontier GPU, or a future thing that hasn't been invented yet.

The problem it solves: ten years ago, if you wanted your code to run on an NVIDIA GPU you wrote CUDA. On AMD, HIP. On Intel, SYCL. On a CPU with vector units, OpenMP. Same loop, four codebases. Worse, the loops aren't even structured the same way — GPUs want millions of tiny independent tasks, CPUs want a few big chunks per thread.

Kokkos hides all of that behind an abstraction called a parallel kernel. You say "for each of these N indices, do this work, and here's how my data is laid out in memory." At compile time Kokkos rewrites that into whatever the target hardware wants.

Demo · 01
Toggle the backend. Watch the same loop change how it executes — but produce the same answer.
Why this matters for gyrokinetics. A production turbulence run touches hundreds of billions of phase-space cells per timestep. Without a portability layer, you bet the next decade of physics on the hardware you wrote for today.

The new code skips Kokkos and uses JAX instead — Google's array library — which plays the same role through a different mechanism: it traces your Python into a hardware-independent intermediate representation and hands that to a compiler (XLA) that emits CPU or GPU code. Different language, same idea: write the math, let the compiler worry about the silicon.

§ 02

Spectral vs grid: how to store a velocity distribution.

Discretization · the f(v) problem

A plasma is described by a distribution function — call it $f(v)$ — telling you how many particles have each velocity $v$. To put this on a computer, you have to discretize it: replace the continuous function with a finite list of numbers.

There are two philosophically different ways to do this, and they have different strengths.

Grid (finite-volume / finite-difference)

  • Pick $N$ velocity values $v_1, v_2, \ldots, v_N$.
  • Store $f(v_1), f(v_2), \ldots, f(v_N)$.
  • Plot looks like a histogram.
  • Good for sharp features (shocks, beams).
  • Need many points to resolve smooth shapes.

Spectral (basis expansion)

  • Pick a set of basis functions $\psi_0, \psi_1, \ldots, \psi_M$.
  • Write $f(v) = c_0\psi_0(v) + c_1\psi_1(v) + \cdots$
  • Store the coefficients $c_0, \ldots, c_M$.
  • Good for smooth shapes (very few coefficients).
  • Bad at sharp features (rings, oscillations).

The spectral basis the new code uses is Hermite–Laguerre: Hermite polynomials in the parallel velocity (along the magnetic field), Laguerre polynomials in the perpendicular kinetic energy. The point — and it's a beautiful one — is that a thermal plasma is approximately a Maxwellian, and a Maxwellian projects onto exactly one Hermite–Laguerre coefficient. Every other coefficient measures how much the plasma deviates from equilibrium. Sparse, by construction.

The tradeoff in one sentence. Spectral methods convert smoothness into compression. If your physics is smooth, you win enormously. If it isn't, you lose.
§ 03

Eulerian vs semi‑Lagrangian: how to push it forward.

Time advance

You have your $f$, stored somehow. Now you need to evolve it in time. The equation governing it is — schematically — a transport equation:

$$\frac{\partial f}{\partial t} + \vec{v}\cdot\nabla f = 0$$

which says: $f$ at a point changes only because stuff is flowing past. There are two strategies for evolving this on a computer, and they are not the same as the two ways of storing $f$ in §02 — you can mix and match.

Eulerian (named for Euler) is the obvious one. You sit at a fixed grid point, you look at the equation, you compute $\partial f/\partial t$ from the spatial derivatives of $f$ around you, and you take a small step in time. Then repeat. Camera bolted to the lab bench, watching fluid flow past.

Lagrangian (named for Lagrange) is the opposite. Don't sit at grid points — ride along with the flow. A pure Lagrangian method tracks particles. The trouble is that after a few timesteps the particles bunch up and starve other regions.

Semi‑Lagrangian is the trick that gets the best of both. Keep a fixed grid (like Eulerian), but at each timestep, for each grid point, ask: where did this $f$ value come from? Trace the velocity field backward in time to the "departure point," then interpolate $f$ from the grid there. You used the Lagrangian idea (follow the flow) but ended up with values on a fixed grid (Eulerian convenience). The phase-space distribution function is conserved along characteristics, so this is actually exact if you could trace and interpolate perfectly.

Demo · 03
A blob of $f$ moves in a swirling velocity field. Watch how each scheme handles the same flow.
The CFL nuance. Eulerian schemes have a hard speed limit on their timestep $\Delta t$: information cannot move more than one cell per step, or the scheme blows up. This is the CFL condition (Courant–Friedrichs–Lewy). Semi-Lagrangian methods have no such limit — the departure point can be three cells back, ten cells back, whatever — which is why they're attractive for long-time simulations. The price is the cost of accurate interpolation, which can introduce its own numerical diffusion.

This is the deepest split between the new code and gyselalib++. The new code is Eulerian (with high-order finite differences and a spectral velocity basis). GYSELA / gyselalib++ are semi-Lagrangian (with a velocity grid). Both are reasonable; they have different failure modes.

§ 04

Landau damping: a wave dies with no friction.

A genuine plasma surprise

Plasmas support waves. Disturb a column of plasma and it oscillates back and forth at a frequency called the plasma frequency. In a fluid description of the plasma, this wave is undamped — once you start it, it rings forever. Lev Landau, in 1946, did the kinetic calculation properly (using the actual distribution function, not just its average) and found something strange: the wave damps. With no collisions. With no friction. In a perfectly collisionless plasma.

This shocked people. Damping without dissipation seems to violate the second law of thermodynamics. It doesn't, but you have to look carefully. Here is what's happening, in pictures:

Demo · 04
A wave with phase velocity $v_\phi$. Particles travelling near $v_\phi$ get pushed by the wave's electric field. Slower particles speed up; faster particles slow down. The wave loses (or gains) energy in the trade.

The mechanism: a wave has a phase velocity $v_\phi = \omega/k$. Particles with velocity close to $v_\phi$ stay near the same phase of the wave for a long time — they surf. A surfer slightly slower than the wave gets nudged forward by the electric field of the wave: it gains energy from the wave. A surfer slightly faster gets pushed back: it gives energy to the wave.

So whether the wave grows or damps comes down to one question: in the distribution, are there more particles slightly slower than $v_\phi$, or slightly faster? Mathematically, it's the sign of the slope of $f(v)$ at $v = v_\phi$:

$$\gamma_L \;\propto\; \left.\frac{\partial f_0}{\partial v}\right|_{v=v_\phi}$$

where $\gamma_L$ is the Landau damping rate. For a Maxwellian, $\partial f_0/\partial v < 0$ everywhere on the right tail (the bell curve slopes down). More slow-surfers than fast-surfers — the wave loses energy. It damps.

Why a code must reproduce this. Landau damping is a fundamental plasma test. It has an exact analytic rate for a Maxwellian. Any kinetic code that doesn't reproduce that number — to several decimal places — is wrong in a way that will silently corrupt every nonlinear turbulence run that comes after.

This is why the new code's roadmap calls out Landau damping as one of the first physics tests in milestone M1. It's a single number ($\gamma_L$) computable analytically, that no fluid model can produce, and that depends on the derivative of $f$ being correct at one specific velocity — exactly the kind of thing your numerical scheme can get plausibly-but-wrongly.

§ 05

ITG growth: the instability that eats fusion plasmas.

The reason gyrokinetic codes exist

The reason fusion is hard: you build a reactor that confines a plasma at 100 million degrees, and the heat leaks out — not through the walls, but through tiny turbulent eddies in the plasma itself. The dominant driver of those eddies, in most fusion devices, is the Ion Temperature Gradient (ITG) instability.

The setup: fusion plasmas are hot in the centre and cold at the edge. So there's a temperature gradient $\nabla T$ pointing radially outward (well, inward in magnitude — temperature drops as you go out). This gradient is unavoidable; it's why the plasma is hot in the middle. But it's also the fuel for an instability.

Sketch of the mechanism, in 2D:

  1. Imagine a small perturbation: a blob of slightly-hotter-than-average plasma displaced outward (toward the cold side).
  2. Hot ions have larger gyroradii than cold ones, so they drift differently in the curved magnetic field. (This is a "curvature drift," a kinetic effect.)
  3. The drift carries the hot blob further outward, and pulls cold plasma inward to fill the gap.
  4. The displacement has grown. So has the temperature contrast. Loop.

This is a positive-feedback loop: the gradient drives a flow that strengthens the gradient. It grows. Exponentially. With a growth rate $\gamma_{\mathrm{ITG}}$ that depends on the steepness of the temperature gradient, the field geometry, and the ion physics:

$$\delta T(t) \;\sim\; \delta T(0)\,e^{\gamma_{\mathrm{ITG}}\, t}$$

The growth saturates when nonlinear effects kick in, and what's left over is a turbulent steady state that carries heat outward 100× faster than collisions would. That outward heat flux is what limits how good a fusion reactor you can build.

Demo · 05
A 2D slice of plasma. Crank the temperature gradient. Watch the ITG eddies grow, saturate, and form a turbulent steady state.

A gyrokinetic code's headline number, in the linear regime, is the ITG growth rate $\gamma_{\mathrm{ITG}}$ as a function of wavenumber $k$. There are decades of cross-code comparison studies (the CYCLONE base case, the Cyclone-DIII-D benchmark) where different codes agree on $\gamma(k)$ to a few percent. When the new code reaches milestone M1, this is one of the curves it has to reproduce.

Why velocity-space matters here. The drift mechanism in step 2 above depends on the distribution of ion velocities. ITG is fundamentally a kinetic instability — fluid models get it qualitatively wrong. That's why fusion needs gyrokinetic codes at all.
§ 06

Rosenbluth–Hinton: the flow that survives.

The number every code must hit

One more concept. In §05 the ITG instability grew exponentially — left to its own devices it would eat the plasma. In reality, it doesn't. The turbulence saturates: the eddies generate large-scale flows that shear them apart. These are zonal flows — flows around the device, in the toroidal direction, with no variation in the poloidal direction (the "short way around"). They're the plasma's immune response to its own turbulence.

Zonal flows are not free, though. If you perturb the plasma with a sudden zonal flow, what happens? Marshall Rosenbluth and Fred Hinton answered this in 1998 with a beautiful calculation. The flow undergoes a damped oscillation called a geodesic acoustic mode (GAM), and then settles to a finite residual level — not zero.

$$\frac{\phi_\mathrm{zonal}(t\to\infty)}{\phi_\mathrm{zonal}(t=0)} \;=\; \frac{1}{1 + 1.6\,q^2/\sqrt{\epsilon}}$$

where $q$ is the safety factor (a geometric property of the magnetic field) and $\epsilon$ is the inverse aspect ratio of the torus. This ratio — the Rosenbluth–Hinton residual — is an exact analytic answer.

Demo · 06
Initial zonal flow at $\phi_0$. Watch it oscillate (the GAM) and settle to a non-zero residual. The dashed line is the Rosenbluth–Hinton prediction.

This is the gold standard test for a gyrokinetic code. The residual depends on:

  • Getting the parallel dynamics of ions right (for the GAM oscillation to have the correct frequency).
  • Getting the polarization response right (for the residual level to be correct).
  • Getting the flux-surface average right (because zonal flows are constants on a flux surface).
  • And the velocity-space integrals have to be accurate, because they appear in both numerator and denominator of the formula above.

Hit Rosenbluth–Hinton to a few percent and you've simultaneously verified four independent parts of your code. Miss it by 20% and something is wrong — but you don't know what. This is exactly the kind of high-information test that the project's "tripwire" philosophy is built around.

The throughline. Each of these six ideas is, in its own way, an attempt to make wrong code fail loudly. Kokkos / JAX so portability doesn't bite you. Spectral methods so smooth distributions compress. Semi-Lagrangian so big timesteps don't blow up. Landau, ITG, Rosenbluth–Hinton — exact answers a wrong code cannot fake. Building the safety net before the physics, so when the physics goes in, you know whether it's right.
